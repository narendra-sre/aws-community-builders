# Article 06 — Automating AWS Infrastructure Deployment with Terraform

This project demonstrates how to deploy and verify a security-conscious Amazon S3 bucket using Terraform. It focuses on reusable modules, Terraform state, controlled infrastructure changes, AWS CLI verification, and automated configuration checks.

## Implementation status

- Terraform configuration deployed successfully; the six planned resources were created.
- S3 versioning, encryption, Block Public Access, and ownership controls verified using AWS CLI.
- Evidence command outputs and deployment screenshots captured.
- Infrastructure cleanup is pending.

> **Cost notice:** This project provisions real AWS resources and is not guaranteed to be free. S3 storage, requests, and other account activity may incur charges. Review current AWS pricing and your account billing before deployment, and destroy the demonstration resources when finished.

## What gets created

- One S3 bucket with a Terraform-generated unique suffix.
- S3 versioning configuration.
- Default SSE-S3 encryption configuration.
- S3 Block Public Access configuration with all four settings enabled.
- Bucket-owner-enforced object ownership controls.
- Project and environment tags.

The bucket uses `force_destroy = false`. If it contains objects or versions, inspect the bucket and remove only demonstration data you intentionally created before destroying it.

## Prerequisites

- Ubuntu 24.04 / WSL2 or another Linux shell.
- Terraform CLI version 1.6 or later.
- AWS CLI v2.
- Locally configured AWS credentials for an identity authorized to manage the S3 resources in this project.
- Network access to download Terraform providers and call AWS APIs.

Use an appropriately scoped IAM identity. Never place access keys, secret keys, session tokens, or AWS credential files in this repository or paste them into chat.

## Configure and initialize

From the project root:

```bash
cp terraform/terraform.tfvars.example terraform/terraform.tfvars
```

Edit `terraform/terraform.tfvars` if needed. The example region is `ap-south-2`; change it if you intend to deploy elsewhere. Terraform generates a random suffix for the bucket name.

```bash
terraform fmt -recursive
terraform -chdir=terraform init
./scripts/terraform-check.sh
```

## Plan and deploy

```bash
./scripts/plan.sh
```

Review the plan. If it contains only the expected resources and settings, apply:

```bash
./scripts/apply.sh
```

Terraform prompts for confirmation. Read the proposed changes before approving.

## Verify and check idempotency

```bash

```

The verification script checks the bucket's public-access block, versioning, encryption, and ownership controls using the bucket name and region returned by Terraform. When the deployed infrastructure matches the configuration, the subsequent plan should report no changes.

## Terraform state

This demonstration uses Terraform's default local state. State files can contain sensitive infrastructure metadata and are excluded by `.gitignore`. Never commit state files, backups, plan files, or credentials.

For team or production deployments, use a protected remote backend with encryption, versioning, access controls, and state locking. This starter project does not create or configure a remote backend automatically.

## GitHub Actions

`.github/workflows/terraform-checks.yml` runs Terraform formatting, initialization, and validation. It does not apply infrastructure and does not require AWS credentials. For a future deployment pipeline, use GitHub OIDC with a narrowly scoped IAM role and protected environment approvals; do not store long-lived AWS keys as repository secrets.

## Cleanup

Destroy resources when evidence collection is complete:

```bash
./scripts/destroy.sh
```

If the bucket contains objects or versions, inspect it and remove only the demonstration data you intentionally created, then rerun destroy. `force_destroy` is disabled to avoid accidental deletion of bucket contents.
